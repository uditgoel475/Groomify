# Groomify

Salon booking backend. Spring Boot + MySQL + Redis, with JWT access / refresh token auth and role-based access for customers and employees. Originally built as a learning project (2019–2020); kept here as a reference implementation of the JWT+refresh flow and a layered Spring Boot service.

> **Not production-ready.** Config files ship with placeholder secrets, the password-history design is intentionally naive (see Caveats), and there are no automated tests beyond a `contextLoads`.

---

## Stack

- Java 8, Spring Boot 2.1, packaged as a WAR (runs embedded or on Tomcat)
- Spring Security + `io.jsonwebtoken` (jjwt 0.9)
- Spring Data JPA / Hibernate + MySQL 5.7+
- Spring Data Redis (token store)
- Spring WebFlux `WebClient` (geonames lookup)
- Springfox Swagger 2.9 (`/swagger-ui.html`)
- Maven

## Auth flow

Access and refresh tokens are kept separately; refresh lives longer, access can be rotated cheaply.

1. **Sign in** (`POST /api/auth/customer/signin` or `/api/auth/employee/signin`)
   - Credentials are verified via `BCryptPasswordEncoder`.
   - On success, `JwtTokenProvider` issues:
     - A short-lived **access JWT** (`HS512`, `app.jwtExpirationInMs` = 15 min default).
     - A long-lived **refresh token** — a random string generated by `RandomStringGenerator`, encrypted with RSA, and stored as the Redis key `TokenType/[refresh]/Token/[<token>]` with the subject payload as value (`app.jwt.refresh.expirationInMs` = 60 days).
   - The access token's Redis entry (`TokenType/[access]/Token/[<token>]`) mirrors the refresh store and is the source of truth validated on each request.
2. **Authenticated request**
   - `JwtAuthenticationFilter` extracts `Authorization` header, calls `tokenProvider.validateAccessToken(jwt)`, which in turn looks up the Redis access entry rather than just verifying signature. That means:
     - Server-side revocation is free — delete the Redis key.
     - Stateless-JWT signature-only validation is not enough; Redis has to be reachable.
3. **Refresh** (`POST /api/auth/{customer,employee}/refreshToken`)
   - Client posts the refresh token; server decrypts, looks up the subject in Redis, issues a fresh access token.

See `security/JwtTokenProvider.java` and `client/RedisHelper.java`.

## Main endpoints

| Path prefix | Purpose |
|---|---|
| `/api/auth/customer`, `/api/auth/employee` | `signin`, `signup`, `refreshToken` |
| `/api/customer` | Customer profile, uploads (profile / govt-id), password change, availability checks |
| `/api/employee` | Employee CRUD, password reset, activities |
| `/api/chair` | Salon-chair allocation by floor + unallocation / expiry |
| `/api/customerorder` | Appointment enquiries, orders, service updates, cancellation |
| `/api/customeremployee` | Cross-entity views (birthdays, etc.) |
| `/api/validatezipcode` | Postal-code validation via geonames.org |

Full surface via Swagger at `http://localhost:8080/swagger-ui.html` once running.

## Running locally

### Prerequisites

- JDK 8
- Maven 3.6+
- MySQL 5.7+ (database auto-created on first run via `createDatabaseIfNotExist=true`)
- Redis 5+
- A geonames.org account (free) for postal-code lookups

### Configure

`src/main/resources/application.properties` ships with placeholders — edit before running:

```properties
spring.datasource.username=<your-mysql-user>
spring.datasource.password=<your-mysql-password>

datasource.redis.master.pass=<your-redis-password>
datasource.redis.slave.pass=<your-redis-password>

# Generate a long random string, e.g. `openssl rand -base64 64`
app.jwtSecret=<64+ char random string>

# Geonames.org username
geoname.postal.codes.by.city=api.geonames.org/postalCodeSearchJSON?placename={city}&username=<your-username>&style=short
geoname.postal.code.validate=http://api.geonames.org/postalCodeLookupJSON?username=<your-username>&postalcode={postalcode}&country={countryCode}&style=short&placename={city}
```

For a real deployment, move these out of `application.properties` into env vars or a secrets manager.

### Build & run

```bash
mvn clean package
java -jar target/groomify-0.0.1-SNAPSHOT.war
```

Or run inside the IDE: `com.uditgoel.groomify.GroomifyApplication`.

## Caveats & known issues

- **Password history** (`dao/Password.java`) stores the last five passwords in five separate columns (`PASSWORD_1..PASSWORD_5`) and rotates them in-place. Works but is not a pattern to copy — a history table keyed by user would be cleaner.
- **Access-token validation hits Redis on every request.** That was a deliberate choice to support server-side revocation, but it also means the service is hard-down if Redis is unavailable. Signature-only validation with a short-lived access token + Redis refresh check would be more common.
- **Spring Boot 2.1 / Java 8 / springfox 2.9** are all end-of-life. A real upgrade would move to Spring Boot 3.x + Java 17 + springdoc-openapi.
- **Git history** contains an old JWT secret from earlier commits. It has been replaced in the current working tree, but anyone cloning the repo can still see the old value in the log. Rotate in any environment that ever used this codebase.
- **Tests are stubs.** The only test is `GroomifyApplicationTests.contextLoads`. Service/controller tests would be the next step.
