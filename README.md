# Groomify

Salon booking backend. Spring Boot 3 + PostgreSQL + Redis, with JWT access / refresh token auth and role-based access for customers and employees. Originally a learning project (2019–2020); kept here as a reference implementation of a stateless-access-token + Redis-backed-refresh-token flow on a layered Spring Boot service.

> **Not production-ready.** Secrets in `application.properties` are placeholders, there are no integration tests beyond a context-load stub, and the reference-data loaders (roles, addresses, geonames) assume a writable seed file. Treat it as a reference for the patterns, not a drop-in service.

---

## Stack

- **Java 17**, **Spring Boot 3.2**, packaged as a WAR (runs embedded or on Tomcat)
- **Spring Security 6** (SecurityFilterChain bean, method security)
- **Spring Data JPA** / Hibernate 6 + **PostgreSQL 13+**
- **Spring Data Redis** (refresh-token store only — access tokens are stateless)
- **jjwt 0.12** for HS512 signing
- **springdoc-openapi 2.3** (`/swagger-ui.html`, OpenAPI at `/v3/api-docs`)
- Spring WebFlux `WebClient` (geonames lookup)
- Maven

## Auth flow

Two token types, intentionally asymmetric:

1. **Sign in** (`POST /api/auth/{customer,employee}/signin`)
   - Credentials verified via `BCryptPasswordEncoder`.
   - On success, `JwtTokenProvider` issues:
     - A short-lived **access JWT** (`HS512`, `app.jwtExpirationInMs` = 15 min default). Subject payload carries id / username / email / user type — AES-encrypted before being placed in `sub` so the token is opaque on the wire.
     - A long-lived **refresh token** — random string generated by `RandomStringGenerator`, RSA-OAEP-encrypted, stored in Redis under `TokenType/[refresh]/Token/[<ciphertext>]` with the subject payload as value (`app.jwt.refresh.expirationInMs` = 60 days).

2. **Authenticated request**
   - `JwtAuthenticationFilter` extracts the bearer header and calls `tokenProvider.validateAccessToken(jwt)`, which is **pure HS512 signature + expiry check — no Redis round-trip**. The subject is decrypted, then the `UserDetails` is loaded by id via `CustomUserDetailsService`.
   - Trade-off: an access token cannot be instantly revoked server-side. With `app.jwtExpirationInMs` = 15 min the window is bounded, which is the normal pattern for stateless JWTs.

3. **Refresh** (`POST /api/auth/{customer,employee}/refreshToken`)
   - Client posts the refresh token. This is the only path that touches Redis: `RedisHelper.getRefreshTokenDetails(...)` looks up the subject and, if present, `tokenProvider.createAccessToken(...)` issues a fresh access JWT. Revoking a session means deleting the Redis key.

See `security/JwtTokenProvider.java`, `security/JwtAuthenticationFilter.java`, and `client/RedisHelper.java`.

## Password storage

- `Password` entity stores the **current** BCrypt hash in a single column plus `pwdCreationDate` / `pwdExpirationDate`.
- `PasswordHistory` is a sibling entity (`@OneToMany` from `Password`) holding the last four previous hashes, newest first.
- On password change, the current hash is moved into history; the new hash becomes current; history is trimmed to `HISTORY_LIMIT`.
- Reuse-check (`getAllPasswordList()`) returns `[current, history...]` so callers can `BCrypt.matches()` the new candidate against each.

| Path prefix | Purpose |
|---|---|
| `/api/auth/customer`, `/api/auth/employee` | `signin`, `signup`, `refreshToken` |
| `/api/customer` | Profile, uploads (profile / govt-id), password change, availability checks |

## Running locally

### Option A — Docker Compose (recommended)

Builds the app, starts Postgres + Redis (+ a Redis Commander UI for inspecting keys),
wires everything together.

```bash
# 1. Generate dev secrets (writes ./.env)
./scripts/generate-env.sh

# 2. Build + start (first run pulls images and builds the app jar in-container)
docker compose up --build

# Swagger UI:      http://localhost:8080/swagger-ui.html
# Redis Commander: http://localhost:8081  (bound to 127.0.0.1 only)
```

Other useful commands:

```bash
docker compose logs -f groomify   # tail app logs
docker compose down               # stop, keep volumes
docker compose down -v            # stop + wipe data volumes
docker compose up -d --build      # rebuild and run detached
```

Once the stack is healthy, load demo data:

```bash
./scripts/seed.sh                                      # 5 demo customers via the public API
GROOMIFY_BASE_URL=https://staging.example ./scripts/seed.sh  # different host
```

The script polls `/v3/api-docs` until the app is ready, posts each customer to
`/api/auth/customer/signup`, then signs in as the first user and fetches their profile to verify
the seed actually landed. Re-running is idempotent — existing rows return 409 and are reported as
"already exists". Edit `scripts/seed/customers.json` to change the data.

Override anything via env vars or by copying `.env.example` → `.env` and editing. The compose file
will refuse to start if `APP_JWT_SECRET`, `APP_AES_KEY`, or the RSA keypair aren't set. Re-running
`generate-env.sh` rotates the secrets (this also invalidates any existing tokens / sessions).

### Option B — Local JDK + already-running Postgres / Redis

Prerequisites: JDK 17, Maven 3.8+, PostgreSQL 13+, Redis 5+, optionally a geonames.org account.

The app reads all secrets from environment variables (`SPRING_DATASOURCE_*`, `APP_JWT_SECRET`,
`APP_AES_KEY`, `RSA_PUBLIC_KEY`, `RSA_PRIVATE_KEY`, `REDIS_*`, `GEONAMES_USERNAME`); see
[`.env.example`](.env.example) for the full list.

```bash
createdb -U postgres groomify
psql -U postgres -c "CREATE USER groomify WITH PASSWORD 'changeme';"
psql -U postgres -c "GRANT ALL PRIVILEGES ON DATABASE groomify TO groomify;"

set -a; source .env; set +a       # load env vars
mvn clean package -DskipTests
java -jar target/groomify-0.0.1-SNAPSHOT.jar
```

Schema is created by Hibernate (`spring.jpa.hibernate.ddl-auto=update`).

### Tests

```bash
mvn test    # 14 tests, ~8s, no Docker / external services required
```

The integration tests boot the full Spring context against an in-process Redis ([embedded-redis](https://github.com/codemonstur/embedded-redis))
and an H2 datasource — no Docker daemon, no Postgres install needed.

## What changed vs. the original version

- **Java 8 → 17**, **Spring Boot 2.1 → 3.2**, **javax.* → jakarta.*** across all entities, filters, and validation annotations.
- **Spring Security 6**: `WebSecurityConfigurerAdapter` removed, replaced with a `SecurityFilterChain` bean; `antMatchers` → `requestMatchers`.
- **jjwt 0.9 → 0.12**: new `Jwts.builder() / Jwts.parser().verifyWith(...)` API, `Keys.hmacShaKeyFor(...)` for the HS512 key.
- **springfox 2.9 → springdoc-openapi 2.3**: OpenAPI 3 annotations and `/v3/api-docs` / `/swagger-ui.html` endpoints.
- **MySQL → PostgreSQL**: driver, JDBC URL, dialect.
- **Spring Data repositories**: `PagingAndSortingRepository<T, ID>` → `JpaRepository<T, ID>` (Spring Data 3 removed CRUD methods from the former).
- **Access-token validation** no longer round-trips Redis — pure signature + expiry check. Redis is only hit on refresh.
- **Password history** redesigned: one current-password column + a `PasswordHistory` table, replacing the five fixed `PASSWORD_1..5` columns.
- **RSA keys** for the refresh-token payload moved out of the source into `rsa.public.key` / `rsa.private.key` properties (OAEP-SHA256 padding, not PKCS#1 v1.5).
- **JWT secret + RSA private key** scrubbed from git history with `git filter-repo`.

## Security notes

- `.env` is gitignored. Never commit it — `scripts/generate-env.sh` produces a fresh
  one each time you need rotation.
- A weak hardcoded HMAC secret was leaked in a 2019 commit and went unnoticed by an
  earlier `git filter-repo` pass. It has since been scrubbed from every blob across
  all branches. The current `JwtTokenProvider` rejects HS512 keys shorter than 64
  bytes at startup, so the leak cannot forge JWTs against the modernized code path,
  but if any pre-modernization deployment is still running with that secret, rotate
  `APP_JWT_SECRET` there immediately.
- A [gitleaks](https://github.com/gitleaks/gitleaks) workflow runs on every push,
  pull request, and weekly via cron — see [`.github/workflows/secret-scan.yml`](.github/workflows/secret-scan.yml)
  and [`.gitleaks.toml`](.gitleaks.toml). The allowlist exempts the deterministic
  test-only fixtures in `src/test/resources/application-test.properties` and the
  empty-placeholder shapes in `.env.example`.

## Caveats & known issues

- **Tests are stubs.** The only test is `GroomifyApplicationTests.applicationClassLoads`. A Testcontainers harness for Postgres + Redis is the next step.
- **Config validation.** The app boots even with placeholder JWT / RSA values, and only errors at first auth. A `@ConfigurationProperties` class with `@Validated` would catch this at startup.
- **Reference-data loaders** (`utils/Load*Table.java`) read seed files from the classpath on startup; they are idempotent but not transactional. Not a problem for a single-instance deployment.
